**تاریخ**: 2026-11-16 | **مبنا**: [spec.md](spec.md) | **راهنمای اجرا**: [quickstart.md](quickstart.md)

## پوشش سناریوها و سطوح

- داستان ۱: AC-101 تا AC-116؛ ایجاد، مالکیت، مشاهده، تکرار، حدود و قالب ورودی و هویت نامعتبر.
- داستان ۲: AC-201 تا AC-206؛ ارسال، مالکیت، منع ویرایش، هویت/مجوز، Submit تکراری و نبود لغو.
- داستان ۳: AC-301 تا AC-316؛ تصمیم مجاز، Self-Approval، وضعیت و مجوز، مشاهده، منع برگشت درخواست خود، محرمانگی و خطا.
- داستان ۴: AC-401 تا AC-407؛ اصلاح، ارسال مجدد، مالکیت، ادامهٔ چرخه و همان قواعد ورودی و Unicode.
- داستان ۵: AC-501 تا AC-508؛ دو ویرایش، دو تصمیم، ویرایش همراه Submit، Rollback و هر دو ترتیب لغو/تصمیم.

این پنج گروه دقیقاً ۵۳ شناسهٔ موجود در Specification را پوشش می‌دهند.
Unit باید استقلال Domain/Application از HTTP را نشان دهد؛ HTTP باید Guard، Pipe، Filter، JWT و parsing واقعی را بررسی کند.
Persistence و Concurrency باید به فایل SQLite واقعی و Migration واقعی متکی باشند؛ Database یا نقش صرفاً Mock‌شده جای آن‌ها را نمی‌گیرد.
برای Unit، test double محدود جهت سنجش یک قاعده مجاز است، اما شاهد یکپارچگی تراکنش محسوب نمی‌شود.

## دروازه‌های اعتبارسنجی آینده

۱. نصب بسته‌های تثبیت‌شده، بارگذاری Native Driver و Migration باید واقعاً موفق شوند.
۲. Build، Unit، HTTP، Persistence، Contract و Concurrency باید با دستور و exit code واقعی ثبت شوند.
۳. بازبینی معماری باید نشان دهد Controller شامل قواعد محصول نیست و SQL در HTTP قرار نگرفته است.
۴. اعتبارسنجی امنیت باید هم Authentication واقعی و هم مجوز جاری داخل تراکنش و محرمانگی پاسخ را بررسی کند.
۵. پذیرش باید معیارهای SC-001 تا SC-015 و رفتار مشاهده‌شده را ارزیابی کند؛ موفقیت تست به‌تنهایی کافی نیست.
۶. مورد اجرا‌نشده، مسدود یا شکست‌خورده نباید تأییدشده گزارش شود.

## بازبینی مستندات در همین مرحله

در این مرحله فقط ساختار طراحی، وجود ارجاع‌ها، تعداد سناریوها، سازگاری تصمیم‌های تأییدشده،
ساختار JSON قرارداد و پیوندهای محلی قابل بررسی‌اند. این شواهد، صحت Runtime، کارایی، Native Driver یا پذیرش محصول نیستند.
قانون اساسی و Specification تغییر نمی‌کنند و Task اجرایی در این فایل تولید نمی‌شود.
