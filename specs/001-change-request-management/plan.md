# برنامهٔ پیاده‌سازی: نسخهٔ اولیهٔ ChangeFlow

**قابلیت**: `001-change-request-management` | **تاریخ**: 2026-11-16 | **مشخصات**: [spec.md](spec.md)

**شاخهٔ واقعی Git**: `main`؛ شناسهٔ قابلیت فعال ابزار Spec Kit برابر `001-change-request-management` است.

**ورودی**: مشخصات نهایی با ۲۷ نیازمندی، ۵۳ سناریو و ۱۵ معیار موفقیت؛
[قانون اساسی نسخهٔ 1.1.0](../../.specify/memory/constitution.md) و [چک‌لیست مشخصات](checklists/requirements.md).

**وضعیت**: پژوهش و طراحی مرحلهٔ Plan تکمیل شده است؛ انتخاب‌های مهم با پاسخ کاربر تأیید شده‌اند.
NestJS به دلیل نزدیکی به پشتهٔ کاربر انتخاب شد؛ Driver مستقیم better-sqlite3 نیز در تأیید تکمیلی پذیرفته شد.
این سند برنامهٔ کار آینده است؛ هیچ پیاده‌سازی یا نتیجهٔ اجرایی از آن استنباط نمی‌شود.

## خلاصه

ChangeFlow یک HTTP API برای ایجاد، اصلاح، ارسال، تأیید و برگشت درخواست تغییر است.
مالکیت، منع Approve و RequestChanges روی درخواست خود، تغییرناپذیری Approved، مجوز جاری،
محرمانگی وجود درخواست و جلوگیری از Lost Update باید مستقل از Controller اعمال شوند.

پشتهٔ مصوب NestJS و TypeScript، SQLite روی یک میزبان محلی و Driver مستقیم better-sqlite3 است.
هر نوشتن در تراکنش کوتاه IMMEDIATE با خواندن مجوز فعلی و نسخهٔ مشاهده‌شده هماهنگ می‌شود.
JWT محلی فقط هویت Development/Test را ثابت می‌کند؛ مجوز فعلی از Database خوانده می‌شود.
تصمیم‌ها، دلایل، گزینه‌های ردشده و منابع رسمی در [research.md](research.md) ثبت شده‌اند.

### جریان مسئولیت و عملیات

۱. Adapter هویت JWT را بررسی و برای عملیات وابسته به id، سیاست اولیهٔ مشاهده را از Application فراخوانی می‌کند.
۲. parsing و اعتبارسنجی HTTP پس از هویت و visibility انجام می‌شوند؛ بدنهٔ خام از خطای زودهنگام parser جلوگیری می‌کند.
۳. Application با هویت معتبر، عملیات نوشتن را به callback همگام IMMEDIATE می‌برد؛ مجوز و درخواست جاری بازخوانی می‌شوند.
۴. قواعد Domain، مجوز، مالکیت، وضعیت و نسخه بررسی و Prepared SQL مشروط اجرا می‌شود؛ پس از Commit موفق پاسخ ساخته می‌شود.
۵. Filter خطا، نتیجه را به دسته و توضیح فارسی نگاشت می‌کند؛ منابع پنهان و ناموجود در همهٔ عملیات پاسخ عمومی یکسان دارند.

در callback تراکنش، هیچ await، شبکه یا انتظار مبتنی بر همان Event Loop نباید باشد.
هیچ Guard یا claim توکن جای بررسی نهایی مجوز را نمی‌گیرد. مسیر داخلی تغییر مجوز نیز همین مرز Database را رعایت می‌کند.
برای نمایش، نقش و درخواست در snapshot سازگار بررسی می‌شوند؛ پاسخ قابل مشاهده ETag دارد و cache نمی‌شود.
برای انتقال موفق 204 بدون نمایش تازه برمی‌گردد؛ حق مشاهدهٔ Reviewer پس از خروج از PendingReview حفظ نمی‌شود.

## پیگیری پیچیدگی

هیچ نقض قانون اساسی نیازمند استثنا وجود ندارد. هزینه‌های ضروری طراحی:

| مورد | دلیل نیاز فعلی | محدودیت گزینهٔ ساده‌تر |
| --- | --- | --- |
| مجوز جاری در همان Database | ترتیب نهایی‌شدن لغو/تصمیم در FR-024 | role claim توکن یا Cache به‌تنهایی کافی نیست. |
| نسخهٔ فنی در قرارداد | تشخیص ورودی مبتنی بر مشاهدهٔ قدیمی | خواندن تازهٔ سرور، قدیمی‌بودن payload مشتری را معلوم نمی‌کند. |
| Parsing پس از Guardها | تقدم 401 و 404 بر خطای اختصاصی منبع پنهان | parser/DTO خطادهندهٔ زودهنگام با قرارداد سخت‌گیرانه سازگار نیست. |
| اتصال‌ها و workerهای مستقل آزمون | اثبات رقابت واقعی writerهای SQLite | Promise.all روی callbackهای همگام یک Event Loop کافی نیست. |
| نگاشت و Migration محدود مستقیم | انتخاب صریح better-sqlite3 برای مرز روشن تراکنش | ORM برای این نیاز کوچک هماهنگی اضافه داشت؛ هزینهٔ نگاشت پذیرفته شد. |
