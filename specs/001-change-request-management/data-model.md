# مدل دادهٔ ChangeFlow

**تاریخ**: 2026-11-16 | **مبنا**: [spec.md](spec.md) | **تصمیم‌ها**: [research.md](research.md)

این سند طراحی است؛ جدول، Migration یا کد برنامه در این مرحله ساخته نمی‌شود.
NestJS، SQLite محلی، مجوز جاری تراکنشی، نسخهٔ فنی و شمارش Unicode scalar تأیید شده‌اند.
Driver مستقیم better-sqlite3 با تأیید تکمیلی کاربر انتخاب شد؛ مدل حاضر در Provider اختصاصی و بدون ORM نگاشت می‌شود.

## موجودیت کاربر و مجوز جاری

نام فنی ذخیره‌سازی `users` است. این موجودیت فقط نگاشت هویت معتبر به مالکیت و نقش فعلی را نگه می‌دارد؛
مدیریت حساب، رمز عبور و Login جزو آن نیستند.

| فیلد | نوع منطقی و قید | دلیل وجود |
| --- | --- | --- |
| id | شناسهٔ یکتای UUID، تولید یا provision توسط سامانه | مالکیت درخواست و ارجاع پایدار |
| issuer | متن غیرخالی از صادرکنندهٔ معتبر | جلوگیری از یکی‌گرفتن subjectهای دو صادرکننده |
| subject | متن غیرخالی، منطبق با sub توکن معتبر | نگاشت هویت؛ از ورودی محتوایی درخواست گرفته نمی‌شود |
| isRequester | مقدار منطقی، پیش‌فرض غیرفعال | مجوز فعلی ایجاد، ویرایش و Submit |
| isReviewer | مقدار منطقی، پیش‌فرض غیرفعال | مجوز فعلی Approve و RequestChanges |

زوج `(issuer, subject)` باید یکتا باشد. برای هر هویت شناخته‌شده یک ردیف پایدار وجود دارد؛
لغو نقش با تغییر مقدار مجوز همان ردیف انجام می‌شود و کاربرِ مالک درخواست حذف نمی‌شود.
کاربر دارای هر دو نقش، هر دو مقدار فعال دارد؛ هیچ پرچمی Self-Approval را مجاز نمی‌کند.
کاربر با هویت معتبر و بدون نقش فعال همچنان طبق FR-019 می‌تواند درخواست‌های خودش را مشاهده کند.

JWT مرجع نقش جاری نیست. provision اولیه و تغییر مجوز مسیر داخلی کنترل‌شدهٔ Development/Test دارند؛
Endpoint عمومی ساخت کاربر، اعطای نقش یا لغو نقش اضافه نمی‌شود.

اگر JWT معتبر باشد ولی زوج `(issuer, subject)` ردیف محلی نداشته باشد، هویت معتبر ولی فاقد مجوز محلی
است؛ ایجاد درخواست با 403 و تمام عملیات وابسته به شناسه با 404 عمومی مصوب رد می‌شوند.
نبود نگاشت باید نتیجه‌ای صریح و متمایز از شکست Database باشد؛ هیچ ردیف یا نقشی خودکار ساخته نشود
و role claim توکن مبنای اعطای مجوز نباشد. شکست Database مطابق قرارداد خطای فنی گزارش می‌شود.

## موجودیت درخواست تغییر

نام فنی ذخیره‌سازی `change_requests` است.

| فیلد | نوع منطقی و قید | منبع و رفتار |
| --- | --- | --- |
| id | UUID یکتا و تغییرناپذیر | تولید سمت سامانه؛ در ایجاد جدید تکرار داده‌ها شناسهٔ جدید می‌سازد |
| title | متن سادهٔ Unicode؛ ۱ تا ۲۰۰ scalar پس از trim | ورودی محتوایی؛ مقدار خالی و فقط فاصله نامعتبر |
| description | متن سادهٔ Unicode؛ ۱ تا ۵۰۰۰ scalar پس از trim | شرح تغییر |
| reason | متن سادهٔ Unicode؛ ۱ تا ۲۰۰۰ scalar پس از trim | دلیل تغییر |
| requesterId | ارجاع اجباری به users.id، تغییرناپذیر | از هویت معتبر و نگاشت محلی تعیین می‌شود |
| status | یکی از Draft، PendingReview، ChangesRequested، Approved | ایجاد فقط Draft؛ تغییر فقط از گردش کار مصوب |
| version | token یکتای UUID و غیرقابل انتخاب توسط مشتری | حفاظت فنی Lost Update؛ پس از هر تغییر موفق تازه می‌شود |

فیلدهای `id` و `version` نیاز فنی قابل دفاع دارند: ارجاع پایدار و تشخیص نسخهٔ مشاهده‌شدهٔ قدیمی.
زمان‌ها، پیوست، برچسب، توضیح بررسی‌کننده و تاریخچهٔ مستقل به محدوده افزوده نمی‌شوند.
هر درخواست دقیقاً یک ثبت‌کننده دارد؛ یک کاربر می‌تواند چند درخواست داشته باشد.

### قیود نگهداری و ورودی

- requesterId و status در پاسخ قابل مشاهده‌اند، اما وجود هرکدام در ورودی ایجاد یا ویرایش، حتی با مقدار درست،
  باعث رد کل عملیات می‌شود. DTO نوشتن فقط title، description و reason دارد.
- مقدارهای محتوایی باید string باشند؛ تبدیل خودکار عدد، مقدار null یا object به متن انجام نمی‌شود.
- ابتدا well-formed بودن Unicode بررسی و سپس فاصله‌های ابتدا و انتها طبق trim حذف می‌شوند؛ شمارش با scalar است.
  طول UTF-16 و تعداد بایت معیار نیستند؛ نیم‌فاصله حفظ می‌شود و normalization زبانی انجام نمی‌شود.
- نشانه‌های HTML و Markdown دادهٔ متنی‌اند؛ سامانه آن‌ها را اجرا یا به قالب غنی تبدیل نمی‌کند.
- قیود Database شامل کلید اصلی، ارجاع مالک، مقدار مجاز وضعیت و اجباری‌بودن فیلدها هستند.
  اعتبارسنجی کسب‌وکار همچنان در Domain/Application لازم است؛ CHECK طول Database جای شمارش Unicode برنامه نیست.
- حذف درخواست و لغو درخواست ارسال‌شده در MVP وجود ندارند؛ FK کاربر نیز نباید حذف زنجیره‌ای درخواست ایجاد کند.

## گردش وضعیت و قابلیت ویرایش

| وضعیت مبدأ | عملیات | مقصد | شرط مجوز و مالکیت |
| --- | --- | --- | --- |
| ایجاد | Create | Draft | Requester فعلی؛ ثبت‌کننده از هویت معتبر |
| Draft | Submit | PendingReview | ثبت‌کننده با مجوز فعلی Requester |
| PendingReview | Approve | Approved | Reviewer فعلی و غیرمالک |
| PendingReview | RequestChanges | ChangesRequested | Reviewer فعلی و غیرمالک |
| ChangesRequested | Submit | PendingReview | ثبت‌کننده با مجوز فعلی Requester |

ویرایش فقط برای مالک دارای مجوز فعلی در Draft و ChangesRequested مجاز است و status را تغییر نمی‌دهد.
Approved قابل ویرایش نیست و انتقال خروجی ندارد. انتقال نامعتبر، خطای ورودی، مجوز و تعارض هیچ تغییر جزئی ندارند.
ویرایش فقط دادهٔ محتوایی را عوض می‌کند؛ انتقال فقط status و version را تغییر می‌دهد.

## نسخهٔ فنی و تغییر اتمیک

- نسخهٔ جاری از طریق ETag فقط برای نتیجهٔ قابل مشاهده ارائه می‌شود؛ نسخهٔ مشاهده‌شده با If-Match به عملیات تغییر می‌رسد.
- version جدید در هر ویرایش یا انتقال موفق، همراه همان تغییر در یک تراکنش ثبت می‌شود.
- شرط نوشتن باید id و version مورد انتظار را شامل شود؛ موفقیت فقط پس از اعمال دقیقاً یک تغییر و Commit اعلام می‌شود.
- مقایسه با نسخه‌ای که سرور تازه خوانده است جای نسخهٔ مشاهده‌شدهٔ مشتری را نمی‌گیرد.
- خطای تطبیق نسخه باعث تغییر، Merge خودکار یا جایگزینی نسخهٔ مشتری نمی‌شود.
- تکرار ایجاد معتبر مستقل است؛ token درخواست، Idempotency Key یا حافظهٔ نتیجهٔ قبلی ساخته نمی‌شود.

## مرز تراکنش و ترتیب لغو مجوز

مجوز جاری و درخواست در یک فایل SQLite قرار می‌گیرند. عملیات نوشتن باید پیش از خواندن مجوز فعلی
با معنای BEGIN IMMEDIATE آغاز شود؛ سپس قابلیت مشاهده، مجوز، مالکیت، وضعیت و نسخه در همان تراکنش بررسی شوند.
Commit مرز نهایی‌شدن است. مسیر داخلی تغییر مجوز نیز باید از همان Database و هماهنگی عبور کند.

اگر لغو مجوز زودتر Commit شود، تصمیم بعدی رد می‌شود؛ اگر تصمیم معتبر زودتر Commit شود، لغو بعدی آن را باطل نمی‌کند.
صرف اعتبار JWT، قفل درون Process یا خواندن مجوز پیش از تراکنش این تضمین را جایگزین نمی‌کند.
برای خواندن نیز نقش و درخواست باید از یک snapshot سازگار ارزیابی شوند تا پاسخ از دو مشاهدهٔ ناسازگار ساخته نشود.

## اطلاعات فنی Migration

جدول فنی `schema_migrations` فقط شمارهٔ Migrationهای اعمال‌شده و checksum آن‌ها را ثبت می‌کند؛
موجودیت یا قابلیت جدید محصول نیست. Migrationها ترتیبی، تغییرناپذیر و پیش از پذیرش ترافیک اجرا می‌شوند.
Reset خودکار داده، synchronize خودکار Schema و اجرای چند Migration هم‌زمان مجاز نیست.
روش اجرای دقیق Migration تابع Driver نهایی است و در راهنمای اجرا مستند می‌شود.
