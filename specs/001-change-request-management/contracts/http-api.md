# قرارداد HTTP API نسخهٔ اولیهٔ ChangeFlow

**تاریخ**: 2026-11-16 | **مبنا**: [مشخصات](../spec.md)، [مدل داده](../data-model.md)، [پژوهش](../research.md)

این قرارداد طراحی است و وجود Endpoint پیاده‌سازی‌شده را اعلام نمی‌کند.
نمای قابل پردازش ابزار در [openapi.json](openapi.json) قرار دارد؛ قواعد ترتیب بررسی و Unicode این سند نیز الزام‌آورند.
مسیر پایه `/api` است؛ نسخه‌بندی عمومی چندنسخه‌ای و Endpointهای خارج از موارد زیر وارد MVP نمی‌شوند.

## هویت و دسترسی

همهٔ عملیات به `Authorization: Bearer` با JWT معتبر نیاز دارند. در حالت Development/Test،
توکن با کلید محلی خارج از مخزن و issuer برابر `changeflow-dev` و audience برابر `changeflow-api` صادر می‌شود.
امضا، الگوریتم مجاز `HS256`، issuer، audience، exp و sub باید بررسی شوند؛ role claim مرجع مجوز جاری نیست.
مجوزها از نگاشت `(issuer, subject)` در `users` خوانده می‌شوند.
JWT معتبر بدون نگاشت محلی، هویت معتبر ولی فاقد مجوز محلی است؛ ایجاد درخواست با 403 و پیام
«اجازهٔ انجام این عملیات را ندارید.» رد می‌شود. تمام عملیات وابسته به شناسهٔ درخواست برای این هویت
همان 404 عمومی مصوب را می‌دهند؛ هیچ درخواست قابل مشاهده‌ای ندارد. کاربر یا نقش خودکار ساخته نمی‌شود
و role claim مجوز ایجاد نمی‌کند. نبود نگاشت با خطای Database متفاوت است؛ شکست زیرساخت طبق قرارداد فنی گزارش می‌شود.
هیچ Login، صدور توکن، تغییر نقش، حذف، لغو یا فهرست عمومی درخواست‌ها Endpoint ندارد.

مالک با هویت معتبر درخواست خود را در همهٔ وضعیت‌ها می‌بیند. Reviewer درخواست دیگران را فقط در
PendingReview می‌بیند. نقش‌های دوگانه مجموع دسترسی مشاهده را دارند، اما Approve و RequestChanges
روی درخواست خود همیشه ممنوع‌اند. مجوز Requester برای ایجاد، ویرایش و Submit لازم است.

## عملیات

| روش و مسیر | ورودی محتوایی | پیش‌شرط و نتیجهٔ موفق |
| --- | --- | --- |
| POST /api/change-requests | title، description، reason | Requester؛ ایجاد Draft؛ پاسخ 201 با نمایش درخواست، Location و ETag |
| GET /api/change-requests/{id} | ندارد | مشاهدهٔ مجاز؛ پاسخ 200 با نمایش درخواست و ETag |
| PUT /api/change-requests/{id} | هر سه مقدار محتوایی | مالک با مجوز Requester در Draft یا ChangesRequested؛ If-Match لازم؛ پاسخ 200 با نمایش تازه و ETag |
| POST /api/change-requests/{id}/submit | بدون محتوا یا شیء خالی | مالک با مجوز Requester در Draft یا ChangesRequested؛ If-Match لازم؛ پاسخ 204 |
| POST /api/change-requests/{id}/approve | بدون محتوا یا شیء خالی | Reviewer غیرمالک در PendingReview؛ If-Match لازم؛ پاسخ 204 |
| POST /api/change-requests/{id}/request-changes | بدون محتوا یا شیء خالی | Reviewer غیرمالک در PendingReview؛ If-Match لازم؛ پاسخ 204 |

روش PUT جایگزینی کامل محتوای درخواست است؛ هر سه مقدار باید ارائه شوند. PATCH برای MVP تعریف نشده است.
تغییر وضعیت پاسخ 204 بدون Body و بدون ETag دارد؛ Reviewer پس از Approve یا RequestChanges دیگر
حق GET درخواست شخص دیگر را ندارد. مالک برای دریافت نمایش و نسخهٔ تازه می‌تواند GET انجام دهد.
پاسخ 204 صرفاً موفقیت همان عملیات است و مجوز مشاهدهٔ تازه ایجاد نمی‌کند.

## نمایش و ورودی

نمایش مجاز شامل `id`، `title`، `description`، `reason`، `requesterId` و `status` است.
نسخه فقط در ETag ارائه می‌شود؛ نیازی به version در ورودی یا Body نمایش نیست.
شناسه‌ها UUID هستند و requesterId از هویت معتبر تعیین می‌شود.

ورودی ایجاد و ویرایش یک شیء JSON با فقط سه مقدار string است. سایر خصوصیت‌ها رد می‌شوند؛
وجود requesterId یا status، حتی null یا برابر با مقدار درست، خطای ورودی است و کل عملیات رد می‌شود.
فیلدهای ناشناخته نباید توسط whitelist بی‌صدا حذف شوند. تبدیل خودکار نوع به string انجام نمی‌شود.
عنوان پس از trim باید ۱ تا ۲۰۰، شرح ۱ تا ۵۰۰۰ و دلیل ۱ تا ۲۰۰۰ Unicode scalar داشته باشد.
Schema با نام WriteChangeRequest در OpenAPI ساختار ورودی خام را توصیف می‌کند؛ حدود بالای طول
روی رشتهٔ خام اعمال نمی‌شوند. پذیرش ساختاری Schema کافی نیست؛ اعتبارسنجی معنایی باید پس از trim
همین حدود را اعمال کند و مقدار trim‌شده را ثبت کند. مقدار دقیقاً در حداکثر مجاز همراه فاصلهٔ بیرونی
باید پذیرفته شود؛ یک scalar بیشتر پس از trim باید کل عملیات را با خطای فیلد رد کند.
ورودی خالی، فقط فاصله، مقدار غیرمتنی یا Unicode ناسالم رد می‌شود؛ surrogate تنها نباید بی‌صدا جایگزین شود.
متن فارسی، لاتین، نیم‌فاصله و ایموجی مجاز است؛ HTML و Markdown صرفاً متن‌اند.

در Node.js شمارش iterator رشتهٔ well-formed، مبنای scalar است؛ طول UTF-16 یا تعداد بایت استفاده نمی‌شود.
trim شامل WhiteSpace و LineTerminator دو سر متن است؛ نیم‌فاصلهٔ درونی حفظ می‌شود.
عنوان تک‌خطی یا حذف شکست خط، محدودیت اضافی این قرارداد نیست؛ ورودی همچنان باید در حدود مصوب بماند.

## نسخه و If-Match

ETag قوی و opaque است و شکل قراردادی آن `"cf-{id}-{version}"` است؛ مشتری باید مقدار دریافتی را بدون
تفسیر داخلی نگه دارد. version یک UUID تازه برای هر ویرایش یا انتقال موفق است.
ویرایش و هر سه عملیات انتقال به یک ETag قوی در If-Match نیاز دارند؛ چند مقدار، wildcard و ETag ضعیف پذیرفته نمی‌شوند.

برای درخواست قابل مشاهده و عملیات مجاز با وضعیت معتبر:

| حالت | پاسخ |
| --- | --- |
| If-Match ارائه نشده | 428 با code برابر VERSION_REQUIRED و توضیح فارسی |
| قالب If-Match نامعتبر | 400 با code برابر INVALID_INPUT و field برابر If-Match |
| ETag مشاهده‌شده با نسخهٔ جاری برابر نیست | 412 با code برابر CONCURRENCY_CONFLICT؛ بدون بازنویسی یا افشای نسخهٔ تازه |
| نسخه برابر و همهٔ قواعد برقرارند | اعمال مشروط اتمیک، نسخهٔ تازه و Commit پیش از اعلام موفقیت |

428 بیانگر نبود پیش‌شرط قراردادی و از خانوادهٔ ورودی نامعتبر است؛ دستهٔ جدید کسب‌وکار نیست.
If-Match ابزار جلوگیری از Lost Update است و نقش Idempotency Key ندارد.
تکرار Submit پس از موفقیت، مادامی که وضعیت PendingReview است، برای مالک خطای وضعیت 409 دارد؛
کنترل نسخه نباید آن را به بازپخش موفقیت قبلی تبدیل کند.
برای Reviewer که با انتقال اول دسترسی مشاهدهٔ خود را از دست داده، تلاش بعدی ابتدا با قاعدهٔ محرمانگی 404 ارزیابی می‌شود.
علت داخلی وضعیت نامعتبر نباید اطلاعات منبع پنهان را به پاسخ عمومی منتقل کند.

## ترتیب بررسی و محرمانگی

پیش از مراحل زیر، سقف فنی دریافت بدنهٔ خام برابر ۱۲۸ KiB یا ۱۳۱۰۷۲ بایت کنترل می‌شود.
بدنهٔ بزرگ‌تر باید هنگام دریافت و پیش از parsing، Authentication و visibility با 413 رد شود؛
این استثنا مستقل از وجود منبع و اعتبار هویت است و هیچ داده‌ای را تغییر نمی‌دهد. پاسخ باید no-store،
با code برابر PAYLOAD_TOO_LARGE، دستهٔ «خطای فنی» و پیام «حجم بدنهٔ درخواست بیش از حد مجاز است»
و بدون اطلاعات منبع، errors، ETag یا Location باشد. اندازهٔ دقیق سقف از کنترل حجم عبور می‌کند؛
این عبور به معنی اعتبار محتوا نیست. برای بدنهٔ در محدوده، ترتیب زیر برقرار است.
سقف بایت، حدود محتوایی scalar پس از trim را تغییر نمی‌دهد؛ JSON escape و فاصلهٔ بیرونی نیز در حجم بدنه حساب می‌شوند.

۱. هویت JWT بررسی شود؛ هویت نامعتبر 401 می‌گیرد و اطلاعات درخواست بررسی یا افشا نمی‌شود.
۲. برای عملیات وابسته به id، نبود درخواست و نداشتن مجوز مشاهده نتیجهٔ عمومی یکسان 404 دارند؛
شناسهٔ نامعتبر نیز نباید امکان تشخیص وجود منبع را ایجاد کند.
۳. برای درخواست قابل مشاهده، مجوز فعلی عملیات و ممنوعیت اقدام روی درخواست خود بررسی شود.
۴. وضعیت فعلی و قواعد عملیات بررسی شوند؛ سپس ورودی محتوایی و پیش‌شرط نسخه ارزیابی شوند.
۵. در عملیات نوشتن، همهٔ بررسی‌های وابسته به داده در تراکنش نهایی دوباره انجام و تغییر مشروط اعمال شود.

برای بدنهٔ در محدودهٔ سقف فنی و حفظ تقدم 401 و 404، adapter نباید JSON نامعتبر یا خطای DTO وابسته به منبع را زودتر از هویت و visibility
به پاسخ اختصاصی تبدیل کند. طراحی Nest از Guardهای اولیه و بدنهٔ خامِ محدود استفاده می‌کند؛ parsing JSON و
اعتبارسنجی معنایی پس از Guardها انجام می‌شود. فعال‌کردن parser خودکارِ خطادهنده پیش از Guardها بدون حفظ
این تقدم مجاز نیست. خطاهای فنیِ غیرقابل‌پردازش در خود پروتکل HTTP مستقل از وجود منبع‌اند و نباید اطلاعات آن را داشته باشند.
Guard برای بررسی اولیه، سیاست Application را فراخوانی می‌کند؛ سیاستی مستقل و متفاوت در HTTP ساخته نمی‌شود.

در نوشتن، هویتِ از قبل اعتبارسنجی‌شده وارد Application می‌شود؛ مجوز، visibility، مالکیت، وضعیت و نسخه
در تراکنش IMMEDIATE با دادهٔ جاری بازخوانی می‌شوند. JWT verification ناهمگام داخل callback تراکنش قرار نمی‌گیرد.
اعتبار زمانی JWT نیز پیش از اعمال نهایی بررسی می‌شود. قفل یا نتیجهٔ Guard جای بررسی نهایی را نمی‌گیرد.

برای 404 ناموجود و خارج از دسترسی، status، code، message، category و ساختار پاسخ یکسان‌اند؛
errors اختصاصی، ETag، Location و جزئیات درخواست در پاسخ وجود ندارند.
پاسخ‌ها باید `Cache-Control: no-store` داشته باشند تا نمایش مجاز قدیمی از cache سامانه به مشاهدهٔ تازه تبدیل نشود.
این قرارداد بر یکسانی محتوای پاسخ متکی است و برابری دقیق زمان شبکه را ادعا نمی‌کند.

## خطاها

پاسخ خطای قراردادی شامل `code`، `category` و `message` فارسی است؛ برای ورودی نامعتبر،
آرایهٔ `errors` شامل `field` فنی و `reason` فارسی ارائه می‌شود. جزئیات داخلی Database، کلید یا JWT بازگردانده نمی‌شوند.
دسته و توضیح به‌صورت زیر نگاشت می‌شوند؛ علت اختصاصی فقط برای درخواست قابل مشاهده ارائه می‌شود.

| HTTP | code | category و نمونهٔ message فارسی |
| --- | --- | --- |
| 400 | INVALID_INPUT | ورودی نامعتبر؛ «اطلاعات ورودی معتبر نیست.»؛ نام فیلد و علت در errors |
| 401 | UNAUTHENTICATED | هویت نامعتبر؛ «احراز هویت معتبر لازم است.» |
| 403 | FORBIDDEN | مجوز ناکافی برای درخواست قابل مشاهده؛ «اجازهٔ انجام این عملیات را ندارید.» |
| 404 | REQUEST_UNAVAILABLE | درخواست در دسترس نیست؛ «درخواست در دسترس نیست.» |
| 409 | INVALID_STATE | وضعیت نامعتبر؛ «این عملیات در وضعیت فعلی مجاز نیست.» |
| 412 | CONCURRENCY_CONFLICT | تعارض هم‌زمان؛ «درخواست پس از مشاهدهٔ شما تغییر کرده است؛ دوباره آن را دریافت کنید.» |
| 413 | PAYLOAD_TOO_LARGE | خطای فنی؛ «حجم بدنهٔ درخواست بیش از حد مجاز است»؛ بدون جزئیات منبع |
| 428 | VERSION_REQUIRED | ورودی نامعتبر؛ «نسخهٔ مشاهده‌شده را در If-Match ارسال کنید.»؛ field برابر If-Match |

401 هدر `WWW-Authenticate: Bearer` دارد. در عملیات وابسته به شناسه، 403 فقط برای منبع قابل مشاهده است؛
برای منبع پنهان 404 مقدم است. ایجاد درخواست بدون مجوز محلی نیز 403 می‌گیرد و منبع موجودی را افشا نمی‌کند.
در محدودهٔ سقف حجم بدنه، عملیات بدنه‌نامعتبر یا If-Match نامعتبر روی منبع پنهان نیز 404 عمومی خواهد داشت.
413 استثنای فنی پیش از بررسی هویت و visibility است و دستهٔ جدید کسب‌وکار محسوب نمی‌شود.
علت نبود نقش جاری، منع Self-Approval یا RequestChanges روی درخواست خود، در محدودهٔ مجوز ناکافی قرار می‌گیرد.

خطای اشغال Database با stale version یکسان نیست. پس از پایان مهلت کوتاه انتظار، شکست زیرساختی 503 با
code برابر SERVICE_UNAVAILABLE و پیام عمومی فارسی ارائه می‌شود؛ خطای پیش‌بینی‌نشده 500 با INTERNAL_ERROR دارد.
این دو خطای اجرایی، دستهٔ جدید قواعد کسب‌وکار یا موفقیت محصول نیستند. هیچ SQL، نام فایل یا stack trace در پاسخ نیست.
مهلت انتظار Database در اجرای محلی ۱۰۰۰ میلی‌ثانیه است؛ retry کاربردی خودکار برای تغییر داده انجام نمی‌شود.
پس از نتیجهٔ نامعلوم Commit، سرور درخواست ایجاد را خودکار دوباره اجرا نمی‌کند.

پاسخ فنی 404 یا 405 بدون افشای وجود درخواست دارد. قرارداد، Login، مدیریت حساب، AI، MCP، Frontend یا قابلیت جدیدی اضافه نمی‌کند.
